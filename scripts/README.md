# سكربتات الإدارة والهجرة

سكربتات تعمل بـ **Firebase Admin SDK**، أي أنها تتجاوز `firestore.rules`
بالكامل. لا تشغّلها إلا من جهاز موثوق، وبمفتاح حساب خدمة محفوظ خارج
المستودع.

```bash
cd scripts && npm install
export GOOGLE_APPLICATION_CREDENTIALS=/path/service-account.json
```

> المفتاح من: Firebase Console ← Project Settings ← Service accounts ←
> Generate new private key. **لا تضعه في Git.**

كل السكربتات تعمل **بوضع المعاينة افتراضياً** ولا تكتب شيئاً إلا مع
`--apply`، وكلها قابلة لإعادة التشغيل بلا أثر جانبي، ولا يحذف أيٌّ منها
بيانات.

---

## ⚠️ ترتيب النشر إلزامي

قواعد «المرحلة صفر» تشترط أشياء لا تحملها البيانات القديمة. تنفيذ الخطوات
بترتيب مقلوب يوقف التطبيق:

| # | الخطوة | لو تخطّيتها |
|---|---|---|
| 1 | `node scripts/grandfather_doctors.js --apply` | **الحجز يتوقف عند كل طبيب** — القواعد تشترط `isVerified` |
| 2 | `node scripts/backfill_phone_index.js --apply` | **الحسابات القديمة لا تستطيع الدخول** — لا فهرس ولا مسار احتياطي |
| 3 | `firebase deploy --only firestore:rules,firestore:indexes` | — |
| 4 | نشر التطبيق (ويب / متجر) | — |

الخطوتان 1 و2 آمنتان قبل النشر: تكتبان حقولاً لا يقرأها الإصدار القديم.

بعد النشر، تحقّق:

```bash
node scripts/grandfather_doctors.js      # يجب أن يكون "سيُوثَّق: 0"
node scripts/backfill_phone_index.js     # يجب أن يكون "سيُكتب مدخل جديد لـ: 0"
```

## ⚠️ ترتيب نشر المرحلة 1أ (محرّك الحجز على الخادم)

الحجز انتقل إلى دالة `bookAppointment`. الخطر هنا **عكسي**: إقفال المسار
القديم قبل أن يستخدم العميل المنشور الدالة يعني أن كل نسخة مثبَّتة على هاتف
مريض تفقد القدرة على الحجز فوراً. ولذلك الإقفال آخر خطوة، لا أولها.

| # | الخطوة | لماذا بهذا الترتيب |
|---|---|---|
| 1 | `firebase deploy --only functions` | الدالة تعمل بـ Admin SDK فتتجاوز القواعد — نشرها وحده لا يكسر شيئاً |
| 2 | نشر التطبيق (ويب / متجر) | العميل يبدأ يستخدم الدالة؛ المسار القديم ما زال مفتوحاً فالنسخ القديمة تعمل |
| 3 | **تحقّق** | احجز فعلياً من التطبيق، وتأكد أن المستند الجديد يحمل `bookedVia: 'callable'` |
| 4 | اقلب `clientDirectBookingEnabled()` إلى `false` في `firestore.rules` | |
| 5 | `firebase deploy --only firestore:rules` | الآن الحجز من الخادم وحده |

للتحقق من الخطوة 3: كل موعد تكتبه الدالة يحمل `bookedVia: 'callable'`، بينما
مواعيد المسار القديم لا تحمل الحقل إطلاقاً. افتح Firebase Console ← Firestore
← `appointments` وافرز على `createdAt` تنازلياً: يجب أن تحمل المواعيد الجديدة
كلها هذا الحقل. وجود موعد حديث بلا `bookedVia` يعني أن عميلاً ما زال يحجز
بالمسار القديم — **لا تقلب المفتاح بعد**.

**متى تقلب المفتاح؟** حين لا تبقى نسخ قديمة فاعلة. على الويب: فوراً بعد
التحقق (المستخدمون يحصلون على الإصدار الجديد من عامل الخدمة). على المتاجر:
انتظر حتى تتبنّى الأغلبية الإصدار الجديد.

الحالتان — قبل القلب وبعده — مغطّاتان باختبارات القواعد، فالقلب لا يحتاج
تجربة على الإنتاج ليُعرف أثره.

### التراجع

اقلب المفتاح إلى `true` وأعد نشر القواعد. الدالة تبقى تعمل، ويعود المسار
القديم — بلا فقدان بيانات.

## `grandfather_doctors.js`

يمنح `isVerified: true` للأطباء الموجودين قبل المرحلة صفر، كما هم.

لا يُنشئ أطباء ولا يغيّر أدواراً، ولا يتخطّى قراراً سابقاً بعدم التوثيق
(`isVerified: false`) إلا مع `--include-rejected`.

## `backfill_phone_index.js`

يملأ `phone_index` من `users` لكل حساب له رقم وبريد.

لا يكتب فوق مدخل قائم؛ التعارضات (رقم مكرر بين حسابين، أو مدخل يشير إلى
مستخدم آخر) تُطبع للمراجعة اليدوية دون لمسها. الحسابات بلا بريد تُطبع أيضاً —
هذه لا تستطيع تسجيل الدخول أصلاً وتحتاج قراراً منك.

توحيد الرقم هنا **نسخة مطابقة** لدالة `normalizePhoneNumber` في التطبيق
(`lib/presentation/providers/firebase_auth_service.dart`). أي اختلاف بينهما
يعني مدخلاً لا يجده التطبيق، أي حساباً معطَّلاً — لا تعدّل أحدهما وحده.

## `promote_to_doctor.js`

الطريق **الوحيد** لصناعة طبيب بعد المرحلة صفر.

```bash
# 1. يسجّل الطبيب حساباً عادياً من التطبيق (كمريض)
# 2. تتحقق من هويته ومزاولته خارج التطبيق
# 3. ترقّيه:
node scripts/promote_to_doctor.js --uid=abc123 --apply
node scripts/promote_to_doctor.js --phone=01001234567 --apply

# ترقية بلا توثيق (يظهر للمرضى بعد التوثيق فقط)
node scripts/promote_to_doctor.js --uid=abc123 --unverified --apply

# سحب التوثيق — الحساب والمواعيد تبقى، ويختفي من البحث
node scripts/promote_to_doctor.js --uid=abc123 --revoke --apply
```

بعد الترقية يكمل الطبيب إعداداته من «إعدادات العيادة» داخل التطبيق:
التخصص، ساعات وأيام العمل، مدة الكشف أو السعة، والسعر.

> السعة التي يعلنها مستند الطبيب (`bookingSystemType` و`maxPatientsPerSlot`)
> صارت هي المرجع الذي تفرضه القواعد على كل خانة، فلا يستطيع العميل رفعها.

## ما ليس هنا (عمداً)

**حذف حساب** — يحتاج تنظيف المواعيد والفهرس والتقييمات معاً، وهو مطلب
إلزامي في متجر Apple. مرحلة لاحقة.

**واجهة إدارة** — لا توجد لوحة أدمن في التطبيق إطلاقاً. هذه السكربتات بديل
مؤقت يفتح الطريق أمام التوثيق، لا حل نهائي.
