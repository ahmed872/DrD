# نموذج الأمان — DrD

هذا التطبيق يخزّن أسماء مرضى وأرقام هواتف وتواريخ ميلاد وأعراضاً وتقييمات
صحية. هذه **بيانات طبية**، والتعامل معها يختلف عن التعامل مع بيانات تطبيق
عادي.

---

## ⚠️ الخطوة الأولى الإلزامية

قبل هذا التحديث لم يكن المستودع يحتوي على `firestore.rules` إطلاقاً — أي أن
قاعدة البيانات تعمل بما ضُبط يدوياً في وحدة تحكم Firebase، وغالباً بوضع
الاختبار المفتوح الذي يسمح لأي شخص على الإنترنت بقراءة كل شيء.

**انشر القواعد فوراً — لكن بالترتيب الصحيح:**

قواعد «المرحلة صفر» تشترط حقولاً لا تحملها البيانات القديمة، فالترتيب المقلوب
يوقف التطبيق (لا حجز عند أي طبيب، ولا دخول للحسابات القديمة):

```bash
node scripts/grandfather_doctors.js --apply     # 1. توثيق الأطباء القائمين
node scripts/backfill_phone_index.js --apply    # 2. فهرسة أرقام الحسابات القديمة
firebase deploy --only firestore:rules,firestore:indexes   # 3.
# 4. ثم نشر التطبيق
```

التفاصيل والضمانات في [`scripts/README.md`](../scripts/README.md).

ثم تحقّق: Firebase Console ← Firestore ← Rules — يجب ألا ترى
`allow read, write: if true;` في أي مكان.

## من يستطيع رؤية ماذا؟

| المجموعة | القراءة | الكتابة |
|---|---|---|
| `users` | صاحب الحساب لمستنده · أي مستخدم مسجَّل لمستندات **الأطباء فقط** | صاحب الحساب، دون تعديل `role` أو `isVerified` أو `email` أو `rating`/`reviews` |
| `phone_index` | مستند واحد بمعرّف معروف (`get` فقط، بلا `list`) | المستخدم المسجَّل لمدخله، وببريده هو |
| `slots` | أي مستخدم مسجَّل | إنشاء بسعة يمليها مستند الطبيب · زيادة بواحد لصاحب الطلب · نقص بواحد لصاحب الحجز وحده · الطبيب لخانات عيادته |
| `appointments` | المريض والطبيب المعنيّان فقط | الإنشاء يستلزم قفل خانة صالحاً في نفس المعاملة · المريض: الإلغاء فقط · الطبيب: الحالة والملاحظة فقط |
| `ratings` | الطرفان المعنيّان فقط | كاتب التقييم |
| `reviews` | أي مستخدم مسجَّل | مريض له موعد **مكتمل** مع الطبيب، ومراجعة واحدة لكل موعد |
| `notifications` | المرسَل إليه فقط | **الخادم فقط** (Cloud Functions) |
| أي مجموعة أخرى | ❌ | ❌ |

### إنشاء الحسابات

| الدور | كيف يُنشأ |
|---|---|
| `patient` | تسجيل ذاتي من التطبيق |
| `doctor` | **Admin SDK فقط**: `node scripts/promote_to_doctor.js --uid=<uid> --apply` |

القواعد تقبل `role == 'patient'` وحده عند الإنشاء، وتمنع أي مستخدم من تعديل
`role` أو `isVerified` لنفسه. لا يوجد طريق من العميل يصنع طبيباً.

### التوثيق شرط للحجز

الحجز (إنشاء خانة أو موعد) لا يُقبل إلا عند طبيب `isVerified == true`. سحب
التوثيق (`--revoke`) يُخفي الطبيب من البحث ويمنع الحجوزات الجديدة عنده، ولا
يمسّ حسابه ولا مواعيده القائمة.

## قرارات تصميمية تستحق الشرح

### 1. لماذا `phone_index` بدل الاستعلام على `users`؟

التطبيق يسمح بتسجيل الدخول برقم الجوال، لكن Firebase Auth يعمل بالبريد
الإلكتروني. لذلك لا بد من ترجمة الرقم إلى بريد **قبل** المصادقة.

الطريقة السابقة كانت:

```dart
await _firestore.collection('users').where('phone', isEqualTo: phone).get();
```

وهذا يفرض السماح بالقراءة العامة لمجموعة `users` كلها — أي أن أي شخص يستطيع
سحب كل الأسماء والأرقام وتواريخ الميلاد والأدوار دون تسجيل دخول.

الآن توجد مجموعة `phone_index` تحتوي على `{uid, email}` فقط، ومعرّف مستندها
هو رقم الجوال. القواعد تسمح بـ `get` وتمنع `list`، فلا يمكن تصفّح المجموعة —
لا بد من معرفة الرقم مسبقاً للوصول لأي مدخل.

**المقايضة بصراحة**: من يعرف رقم جوال شخص يستطيع معرفة بريده الإلكتروني.
هذا أضعف بكثير من كشف قاعدة المستخدمين كاملة، لكنه ليس صفراً. للإغلاق
التام، حوّل الترجمة إلى Cloud Function بمعدّل محدود
(callable + rate limiting) وأغلق `phone_index` نهائياً.

### 2. هجرة الحسابات القديمة

كان `_resolveEmailForPhone` يسقط لاستعلام على `users` عند غياب المدخل، ثم
يكتب المدخل الناقص — هجرة تدريجية مع كل تسجيل دخول. حُذف ذلك المسار: هو
يتطلب قراءة `users` قبل المصادقة (أي كشف كل الأسماء والأرقام وتواريخ
الميلاد)، والقواعد الحالية ترفضه أصلاً فصار كوداً ميتاً يوحي بأمان غير موجود.

البديل هجرة صريحة تُشغَّل مرة واحدة بصلاحيات المدير:

```bash
node scripts/backfill_phone_index.js --apply
```

**هذه الخطوة إلزامية قبل النشر** — بدونها لا يستطيع أي حساب قديم بلا مدخل
تسجيل الدخول. راجع `scripts/README.md` لترتيب النشر كاملاً.

### 3. لماذا لا يستطيع المستخدم تغيير `role`؟

```javascript
function keepsProtectedFields() {
  return request.resource.data.role == resource.data.role
      && request.resource.data.get('isVerified', false)
         == resource.data.get('isVerified', false)
      && ... // email, rating, reviews
}
```

بدون شرط `role` يستطيع أي مريض ترقية نفسه إلى `doctor` من العميل مباشرة،
فيرى مواعيد العيادة ومرضاها. وبدون شرط `isVerified` يوثّق الطبيب نفسه فتسقط
قيمة التوثيق كلها.

`phone` غير محمي عمداً — شاشة إعدادات الطبيب تعدّله. مزامنة `phone_index`
مسؤولية التطبيق.

### 3.05 من يقرّر الحجز؟ (المرحلة 1أ)

الخادم. الحجز يمرّ عبر الدالة `bookAppointment` (راجع `functions/booking.js`)،
والعميل يرسل **طلباً** لا قراراً:

```
{ doctorId, date: 'yyyy-MM-dd', time: 'HH:mm', reason? }
```

كل ما عدا ذلك يستخرجه الخادم من Firestore: السعر، السعة، مدة الكشف، وقت
النهاية، اسم الطبيب وتخصصه وعنوان عيادته، اسم المريض ورقمه، حالة الموعد،
ومعرّفات المستندات. القيم التي يرسلها العميل لهذه الحقول **تُتجاهل بالكامل**.

قبل ذلك كانت هذه الحقول تُكتب كما يرسلها العميل: `price: 1` كان يُقبل، ولم
يكن هناك ما يمنع حجز الساعة 03:00 فجراً لأن لا شيء كان يقارن الوقت بجدول
الطبيب أصلاً.

المعاملة الذرّية لم تتغيّر — انتقلت كما هي إلى الخادم.

`clientDirectBookingEnabled()` في `firestore.rules` هو مفتاح إقفال المسار
القديم، ويُقلب في خطوة نشر مستقلة بعد التحقق (`scripts/README.md`).

### 3.06 من يقرّر الإلغاء وإعادة الجدولة والتوفّر؟ (المرحلة 1ب)

الخادم أيضاً، بنفس المبدأ: `cancelAppointment` و`rescheduleAppointment`
(راجع `functions/lifecycle.js`) و`getAvailability` (راجع
`functions/availability.js`) تستقبل طلبات لا قرارات.

كانت القاعدة تسمح للمريض بإلغاء موعده مباشرة بلا أي تحقق من الحالة أو
المهلة — يستطيع مريض إلغاء موعد بعد بدايته، أو موعد مكتمل بالفعل، بضغطة
واحدة. والآن `cancelAppointment` تتحقق من الملكية، وحالة الموعد
(`isCancellable`)، ومهلة لا يجوز الإلغاء بعدها (ساعة قبل الموعد افتراضياً)،
قبل تحرير الخانة في نفس المعاملة الذرّية.

إعادة الجدولة لم تكن موجودة إطلاقاً قبل هذه المرحلة. `rescheduleAppointment`
تكتب موعداً **جديداً** بالمعرّف الحتمي المشتق من الخانة الجديدة، وتُبقي
القديم بحالة `Cancelled` مع `rescheduledTo` يشير إلى الجديد — فيبقى سجل
العيادة كاملاً بدل أن يُستبدَل. تحرير الخانة القديمة وحجز الجديدة وربط
المستندين يتم كله في معاملة واحدة: إما ينجح كل شيء أو لا يتغيّر شيء.

`getAvailability` تستخدم **نفس** دوال الجدول التي يستخدمها الحجز وإعادة
الجدولة (`assertSlotWithinSchedule`, `generateSlotTimes`, `isWorkingDay`)،
فلا تعرض وقتاً يرفضه الحجز لاحقاً. الطلب لا يحمل سعة ولا عدّادات من
العميل — معرّفات ومدى تاريخ فقط؛ الرد وحده يحملهما من Firestore، وهو مع
ذلك ليس مرجعاً نهائياً: معاملة الحجز تبقى الحكم الأخير دائماً.

`clientDirectCancelEnabled()` في `firestore.rules` هو مفتاح إقفال إلغاء
المريض المباشر، بنفس انضباط `clientDirectBookingEnabled()` (راجع
`scripts/README.md`). إعادة الجدولة لم يكن لها مسار مباشر لتُقفَل. إلغاء
**الطبيب** لموعد مريضه من شاشة جدوله يبقى بمساره المباشر القديم عمداً —
خارج نطاق هذا المفتاح، لأن القواعد تمنحه أصلاً حرية إدارة خانات عيادته.

### 3.1 لماذا لا يقوم الموعد بذاته؟

إنشاء مستند في `appointments` يستلزم أن يقابله قفل في `slots` يحمل نفس
الطبيب والتاريخ والوقت ويحتوي صاحب الطلب، ويُفحص بـ `getAfter` لأن الاثنين
يُكتبان في **نفس المعاملة**. ومعرّف المستند مقيَّد بـ `{slotId}__{patientId}`.

بدون ذلك كان ضمان عدم الحجز المزدوج قابلاً للتخطي كلياً: يكفي أن يكتب عميل
معدَّل مستند موعد مباشرة بلا مرور على أي قفل، والطبيب يراه في جدوله لأن
الجدول يُقرأ من `appointments` لا من `slots`.

### 3.07 من يقرّر صلاحية الإدارة وتوثيق الأطباء؟ (المرحلة 2)

صلاحية `admin` **Custom Claim** داخل رمز Firebase Auth الموقَّع
(`request.auth.token.admin` في القواعد، `context.auth.token.admin` في
الدوال السحابية) — لا حقل Firestore إطلاقاً. لا يكتبها إلا Admin SDK عبر
`scripts/create_admin.js`، ولا يوجد أي مسار عميل يمنحها لنفسه أو لغيره.

دورة حياة توثيق الطبيب:

```
تسجيل كمستخدم عادي (role: patient)
        │
        ▼
doctorApplications/{uid}.status = 'pending'   (كتابة مباشرة من العميل،
        │                                       تحكمها القواعد وحدها)
        ├── approveDoctor ──► users/{uid}: role='doctor', isVerified=true,
        │                     disabled=false
        └── rejectDoctor ──► doctorApplications/{uid}.status='rejected'
                              (لا يُلمس users/{uid} إطلاقاً)

طبيب نشط (role=doctor, isVerified=true, disabled=false)
        ├── suspendDoctor ──► disabled=true   («موثَّق لكن موقوف»)
        └── restoreDoctor ──► disabled=false
```

`isVerified` و`disabled` هما الحقلان اللذان تفحصهما `fetchBookableDoctor`
في `availability.js` — وهي دالة موجودة منذ المرحلة 1أ، وكانت تفحص
`doctor.disabled` بلا أن يكتبه أي كود قط. المرحلة 2 لم تُعدِّل محرّك الحجز
إطلاقاً؛ هي أول من يكتب هذا الحقل فعلياً.

الحقول الأربعة (`approveDoctor`/`rejectDoctor`/`suspendDoctor`/
`restoreDoctor`) دوال سحابية فقط — Firestore Rules تمنع أي كتابة عميل على
`disabled` أو `verificationStatus` أو أي حقل من حقول سجل التوثيق (حتى من
صاحب الحساب نفسه)، وتمنع أي كتابة على `doctorApplications/{uid}.status`
خارج `pending`، فلا مسار عميل — ولو حمل صلاحية admin — يستطيع تغيير هذه
الحالة مباشرة عبر Firestore؛ فقط الدوال السحابية، وكل إجراء منها يُسجَّل في
`auditLogs` (append-only، قراءة للإدارة فقط، كتابة من Admin SDK حصراً).

### 4. لماذا الإشعارات لا تُنشأ من العميل؟

`allow create: if false;` — لأن Cloud Functions تتجاوز قواعد الأمان، بينما
العميل لا يجب أن يستطيع إرسال إشعار باسم العيادة لمستخدم آخر.

### 5. لماذا لا يُحذف أي موعد؟

`allow delete: if false;` — الإلغاء يتم بتغيير الحالة إلى `Cancelled`، حتى
يبقى سجل العيادة كاملاً وقابلاً للمراجعة، ولا يستطيع أحد محو دليل على موعد.

### 6. لماذا حُذفت مجموعة `otps`؟

كانت القاعدة `allow create: if true` — كتابة بلا مصادقة إطلاقاً — ودالة
سحابية (`sendOTPEmail`) ترسل بريداً إلى العنوان المأخوذ من **معرّف المستند**.
أي أن أي شخص على الإنترنت يكتب مستنداً معرّفه بريد أي ضحية فيصلها بريد من
عنوان المشروع: **مرحّل بريد مفتوح**، تصيّد باسم العيادة وحرق لسمعة نطاق
الإرسال، وفاتورة إرسال على حساب المشروع.

المسار لم يكن مستخدماً في التطبيق أصلاً — الدخول ببريد وكلمة مرور عبر
Firebase Auth. حُذفت الدالة والمجموعة وتبعية `nodemailer` وأسرار البريد.

### 7. لماذا تشترط المراجعة موعداً مكتملاً؟

كانت `reviews` تقبل أي مراجعة من أي حساب مسجَّل، بلا حد ولا منع تكرار —
فيستطيع منافس واحد إنزال تقييم طبيب إلى الصفر في دقائق.

الآن معرّف المراجعة **هو معرّف الموعد**، والقاعدة تقرأ ذلك الموعد وتتأكد أنه
يخصّ صاحب الطلب، وأنه عند الطبيب نفسه، وأن حالته مكتملة. فالمراجعة شهادة على
زيارة حدثت، وواحدة لكل زيارة.

## ما ليس سرّاً

`apiKey` في `firebase_options.dart` و`google-services.json` **ليست أسراراً**.
Firebase يرسلها للعميل بالضرورة، وهي موجودة في أي تطبيق ويب منشور. ما يحمي
البيانات هو `firestore.rules` وحدها.

الأسرار الحقيقية في هذا المشروع:
- `android/key.properties` و`*.jks` (توقيع أندرويد) — مُستثناة من Git
- مفتاح حساب الخدمة الذي تستخدمه سكربتات `scripts/` — لا يدخل Git إطلاقاً

(لم تعد الدوال السحابية تحتاج أي أسرار بعد حذف مسار البريد.)

| البند | الحالة | التوصية |
|---|---|---|
| التحقق من البريد الإلكتروني | **معطَّل** في الكود (`sendEmailVerification` معلّقة، و`emailVerified: true` تُكتب دائماً) | فعّله قبل الإطلاق العام — بدونه يمكن التسجيل ببريد شخص آخر |

| احتكار رقم جوال غير مسجَّل | ممكن — من يكتب مدخل `phone_index` أولاً يمنع تسجيل صاحب الرقم | يحتاج تحقّقاً فعلياً من ملكية الرقم (Firebase Phone Auth) |
| سياسة الخصوصية | غير موجودة | **إلزامية** لمتجري Apple وGoogle عند جمع بيانات صحية |
| حذف الحساب | غير مدعوم | **إلزامي** في متجر Apple — يحتاج Cloud Function تنظّف المواعيد والفهرس والتقييمات |
| تحديد معدّل الطلبات | غير موجود | Firebase App Check يمنع إساءة استخدام قاعدة البيانات من عملاء غير التطبيق |
| لوحة إدارة | غير موجودة | التوثيق والترقية تتم بسكربتات `scripts/` مؤقتاً |

## اختبار القواعد محلياً

القواعد مغطّاة بـ 77 اختباراً تعمل على محاكي Firestore الحقيقي — تُثبت المنع
فعلاً لا بقراءة الملف:

```bash
npm --prefix test/firestore_rules install
firebase emulators:exec --only firestore --project drd-rules-test \
  "npm --prefix test/firestore_rules test"
```

تعمل تلقائياً في CI على كل دفعة (`.github/workflows/ci.yml`).

الاختبارات تحاكي المسار الحقيقي للتطبيق: الحجز يكتب القفل والموعد في
**معاملة واحدة** (`writeBatch` / `runTransaction` مع `arrayUnion`)، لأن
اختبار كتابات منفردة كان سيختبر قواعد لا تشبه ما يفعله التطبيق — ولن يكشف
مثلاً أن `getAfter` هي وحدها ما يجعل ربط الموعد بالقفل ممكناً.

من الحالات المغطّاة: تجاوز سعة الخانة، رفع السعة، إنشاء حساب طبيب، توثيق
ذاتي، إنقاص عدّاد خانة ليست لك، إخراج مريض آخر من خانة مجموعة، موعد بلا قفل،
تعديل المريض لحقول محمية، مراجعة بلا زيارة، ومراجعة مكرّرة.
