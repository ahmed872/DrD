# نموذج الأمان — DrD

هذا التطبيق يخزّن أسماء مرضى وأرقام هواتف وتواريخ ميلاد وأعراضاً وتقييمات
صحية. هذه **بيانات طبية**، والتعامل معها يختلف عن التعامل مع بيانات تطبيق
عادي.

---

## ⚠️ الخطوة الأولى الإلزامية

قبل هذا التحديث لم يكن المستودع يحتوي على `firestore.rules` إطلاقاً — أي أن
قاعدة البيانات تعمل بما ضُبط يدوياً في وحدة تحكم Firebase، وغالباً بوضع
الاختبار المفتوح الذي يسمح لأي شخص على الإنترنت بقراءة كل شيء.

**انشر القواعد فوراً:**

```bash
firebase deploy --only firestore:rules
```

ثم تحقّق: Firebase Console ← Firestore ← Rules — يجب ألا ترى
`allow read, write: if true;` في أي مكان.

## من يستطيع رؤية ماذا؟

| المجموعة | القراءة | الكتابة |
|---|---|---|
| `users` | صاحب الحساب لمستنده · أي مستخدم مسجَّل لمستندات **الأطباء فقط** | صاحب الحساب، دون تعديل `role` أو `rating` أو `reviews`. **الإنشاء بدور `patient` حصراً** |
| `phone_index` | مستند واحد بمعرّف معروف (`get` فقط، بلا `list`) | المستخدم المسجَّل لمدخله |
| `slots` | أي مستخدم مسجَّل | زيادة/نقص بواحد فقط ودون تجاوز السعة |
| `appointments` | المريض والطبيب المعنيّان فقط | **مفصولة بالحقل**: المريض يلغي فقط · الطبيب يكتب الحالة والبيانات السريرية · لا أحد ينقل الموعد |
| `ratings` | الطرفان المعنيّان فقط | كاتب التقييم |
| `reviews` | أي مستخدم مسجَّل | صاحب المراجعة |
| `notifications` | المرسَل إليه فقط | **الخادم فقط** (Cloud Functions) |
| أي مجموعة أخرى | ❌ | ❌ |

> `otps` أُزيلت بالكامل — القاعدة والدالة معاً. راجع "ما تغيّر في المرحلة صفر".

## قرارات تصميمية تستحق الشرح

### 1. لماذا `phone_index` بدل الاستعلام على `users`؟

التطبيق يسمح بتسجيل الدخول برقم الجوال، لكن Firebase Auth يعمل بالبريد
الإلكتروني. لذلك لا بد من ترجمة الرقم إلى بريد **قبل** المصادقة.

الطريقة السابقة كانت:

```dart
await _firestore.collection('users').where('phone', isEqualTo: phone).get();
```

وهذا يفرض السماح بالقراءة العامة لمجموعة `users` كلها — أي أن أي شخص يستطيع
سحب كل الأسماء والأرقام وتواريخ الميلاد والأدوار دون تسجيل دخول.

الآن توجد مجموعة `phone_index` تحتوي على `{uid, email}` فقط، ومعرّف مستندها
هو رقم الجوال. القواعد تسمح بـ `get` وتمنع `list`، فلا يمكن تصفّح المجموعة —
لا بد من معرفة الرقم مسبقاً للوصول لأي مدخل.

**المقايضة بصراحة**: من يعرف رقم جوال شخص يستطيع معرفة بريده الإلكتروني.
هذا أضعف بكثير من كشف قاعدة المستخدمين كاملة، لكنه ليس صفراً. للإغلاق
التام، حوّل الترجمة إلى Cloud Function بمعدّل محدود
(callable + rate limiting) وأغلق `phone_index` نهائياً.

### 2. هجرة الحسابات القديمة

الحسابات المنشأة قبل هذا التحديث ليس لها مدخل في `phone_index`. لذلك يسقط
`_resolveEmailForPhone` للطريقة القديمة عند عدم وجود مدخل، **ويكتب المدخل
الناقص تلقائياً** — فتُهاجَر الحسابات تدريجياً مع كل تسجيل دخول.

**هذا يعني أن `users` ما زالت تحتاج قراءة أوسع مؤقتاً.** بعد اكتمال الهجرة:

1. تحقّق أن عدد مستندات `phone_index` يساوي عدد المستخدمين
2. احذف المسار الاحتياطي من `_resolveEmailForPhone`
3. شدّد قاعدة `users` لتقتصر على `isUser(userId)` وحده

يمكن تسريع الهجرة بسكربت إداري (Admin SDK) يمرّ على `users` ويكتب الفهرس
دفعة واحدة.

### 3. الدور لا يختاره العميل — لا عند الإنشاء ولا بعده

بابان كان لا بد من إغلاقهما معاً:

```javascript
// عند الإنشاء — كانت `role in ['doctor', 'patient']`
allow create: if isUser(userId)
              && request.resource.data.role == 'patient';

// وبعد الإنشاء
function keepsProtectedFields() {
  return request.resource.data.role == resource.data.role
      && /* rating و reviews كذلك */;
}
```

القاعدة الثانية كانت موجودة، لكن الأولى لم تكن: شاشة التسجيل كانت تعرض زرّي
"مريض / طبيب"، والقاعدة تقبل الاختيار. أي أن منع الترقية *بعد* الإنشاء لم يكن
يعني شيئاً — يكفي أن تختار "طبيب" من البداية.

`phone` غير محمي هنا عمداً: شاشة إعدادات الطبيب تسمح بتعديل الرقم.
**تنبيه**: التطبيق لا يزامن `phone_index` عند تغيير الرقم، فالطبيب الذي يغيّر
رقمه يفقد القدرة على تسجيل الدخول به. مسجَّل كمخاطرة مؤجَّلة أدناه.

### 3‑ب. سلطة البيانات السريرية

مستند الموعد يحمل بيانات حجز يكتبها المريض، وبيانات سريرية يكتبها الطبيب
وتُعرض للمريض لاحقاً كـ"سجله الطبي". القاعدة القديمة كانت تسمح لكلا الطرفين
بالكتابة في كل الحقول عدا أربعة، أي أن **المريض كان يستطيع مسح ملاحظة الطبيب،
وكتابة تشخيص، وتعليم الموعد "مكتمل" فيصنع زيارة لم تحدث**.

الفصل الآن على مستوى الحقل بقائمتَي سماح:

| الطرف | ما يجوز له تغييره |
|---|---|
| المريض | `status` (إلى `Cancelled` فقط، ولموعد غير منتهٍ) + `cancelledAt` |
| الطبيب | `status`, `cancelledAt`, `completedAt`, `updatedAt`, `notes`, `diagnosis`, `prescription`, `treatment` |
| لا أحد | `doctorId`, `patientId`, `appointmentDate`, `startTime`, `price`, `reason`, `patientName`, `patientPhone` |

وعند **الإنشاء** تُمنع الحقول السريرية تماماً، وإلا أمكن حجز موعد ومعه
`diagnosis` جاهز يظهر في السجل الطبي بمجرد أن يُنهي الطبيب الكشف.

### 3‑ج. الاستعلام يجب أن يطابق القاعدة

هذا ليس تفصيلاً نظرياً — إنه سبب تعطُّل شاشتين في الإنتاج.

Firestore يرفض **الاستعلام كاملاً** إذا كان أي مستند في نتيجته يخالف القاعدة.
فاستعلام "كل مواعيد الطبيب في يوم" يعيد مواعيد مرضى آخرين، وقاعدة الموعد تسمح
لطرفيه وحدهما، فيُرفض الاستعلام كله لحساب المريض:

```dart
// مرفوض للمريض — نتيجته تشمل مواعيد غيره
.where('doctorId', isEqualTo: id).where('appointmentDate', isEqualTo: d)

// مقبول — مقيَّد بصاحب الطلب
.where('doctorId', isEqualTo: id)
.where('patientId', isEqualTo: myUid)
.where('appointmentDate', isEqualTo: d)
```

الاستدعاء كان يلتقط الاستثناء ويسجّله، فبدا العطل كأنه "لا توجد بيانات".

**قاعدة العمل**: كل استعلام في التطبيق له اختبار يثبت نجاحه للدور الشرعي، لا
اختبار منع المهاجم وحده. راجع `describe('مطابقة الاستعلامات بالقواعد')` في
`test/firestore_rules/rules.test.js`.

### 4. لماذا الإشعارات لا تُنشأ من العميل؟

`allow create: if false;` — لأن Cloud Functions تتجاوز قواعد الأمان، بينما
العميل لا يجب أن يستطيع إرسال إشعار باسم العيادة لمستخدم آخر.

### 5. لماذا لا يُحذف أي موعد؟

`allow delete: if false;` — الإلغاء يتم بتغيير الحالة إلى `Cancelled`، حتى
يبقى سجل العيادة كاملاً وقابلاً للمراجعة، ولا يستطيع أحد محو دليل على موعد.

## ما ليس سرّاً

`apiKey` في `firebase_options.dart` و`google-services.json` **ليست أسراراً**.
Firebase يرسلها للعميل بالضرورة، وهي موجودة في أي تطبيق ويب منشور. ما يحمي
البيانات هو `firestore.rules` وحدها.

الأسرار الحقيقية في هذا المشروع:
- `functions/.env` (بيانات بريد الإرسال) — مُستثنى من Git
- `android/key.properties` و`*.jks` (توقيع أندرويد) — مُستثناة من Git

## ما تغيّر في المرحلة صفر

| # | كان | صار |
|---|---|---|
| 1 | أي شخص يسجّل نفسه طبيباً من شاشة التسجيل | الإنشاء بدور `patient` حصراً؛ أُزيل اختيار الدور من الواجهة |
| 2 | المريض يكتب `notes` و`diagnosis` ويعلّم الموعد "مكتمل" | فصل الحقول: المريض يلغي فقط، والطبيب وحده يكتب السريري |
| 3 | شاشة مرضى الطبيب فارغة دائماً (قراءة `users` مرفوضة) | تُبنى من مستندات المواعيد؛ لم تُفتح أي صلاحية جديدة |
| 4 | كل الأوقات تظهر متاحة (استعلام `appointments` مرفوض) | الإشغال يُقرأ من `slots`؛ وفشل التحميل يُعرض بدل ادّعاء التوفّر |
| 5 | `otps` تسمح بالإنشاء بلا مصادقة + دالة ترسل بريداً لأي عنوان | أُزيلت القاعدة والدالة و`nodemailer` معاً |
| 6 | مقارنات نصية للحالة موزّعة على الشاشات | كلها عبر `AppointmentStatus.parse`؛ الكتابة بـ `wireValue` |

المعاملة الذرّية للحجز وقاعدة سعة الخانة **لم تتغيّرا**، وتغطيهما اختبارات
الانحدار كما كانت.

## خطة هجرة مؤجَّلة: خانات المواعيد القديمة

المواعيد المحجوزة قبل نظام الأقفال ليس لها مستند في `slots`، فلا تظهر في
حساب الإشغال ولا تمنع حجز نفس الوقت. كان هناك فحص احتياطي
(`_findLegacyConflict`) لكنه كان يستعلم استعلاماً مرفوضاً، فلم يكن يفحص شيئاً
منذ نُشرت القواعد — وقد أُزيل بدل تركه يوهم بحماية غير موجودة.

**لا تُنفَّذ هذه الهجرة تلقائياً.** عند الحاجة، سكربت Admin SDK يمرّ على
`appointments` ذات الحالة المشغولة ويُنشئ مستند الخانة الناقص:

```
slots/{doctorId}_{appointmentDate}_{startTime بشرطة}
  → { doctorId, appointmentDate, startTime, capacity, bookedCount, patientIds }
```

يجب تشغيله مرة واحدة، على نسخة احتياطية أولاً، مع التحقق من عدم الكتابة فوق
خانة قائمة.

## نقاط تحتاج انتباهك

| البند | الحالة | التوصية |
|---|---|---|
| التحقق من البريد الإلكتروني | **معطَّل** (`sendEmailVerification` معلّقة، و`emailVerified: true` تُكتب دائماً) | تفعيله يمنع دخول كل الحسابات القائمة، فهو يحتاج خطة استثناء لها. مؤجَّل عمداً — ليس تعديلاً بسطر واحد |
| ترقية حساب إلى طبيب | يدوياً من وحدة تحكم Firebase | نظام الطلبات ومراجعة المشرف — المرحلة التالية |
| `slots.patientIds` | مقروء لأي مستخدم مسجَّل، ويكشف مَن حجز عند مَن ومتى | نقل فحص "المريض حاجز بالفعل" إلى قراءة مستند الموعد ذي المعرّف المحسوب، ثم حذف الحقل. لم يُنفَّذ الآن لأنه يمسّ معاملة الحجز نفسها |
| بيانات الطبيب الشخصية | `email` و`birthDate` مقروءة لكل مستخدم مسجَّل | القواعد لا تفلتر الحقول عند القراءة؛ الحل فصل ملف عام عن مستند الهوية — يحتاج تغييراً معمارياً |
| `phone_index` عند تغيير الرقم | لا يُزامَن | إصلاحه يعني كتابة/حذف مدخلين في معاملة، وقد يتعارض مع مدخل قائم |
| الحد الأدنى لكلمة المرور | 6 أحرف | ارفعه إلى 8 على الأقل لتطبيق طبي |
| سياسة الخصوصية | غير موجودة | **إلزامية** لمتجري Apple وGoogle عند جمع بيانات صحية |
| حذف الحساب | غير مدعوم | **إلزامي** في متجر Apple — يحتاج Cloud Function تنظّف المواعيد والفهرس والمشاركات |
| تحديد معدّل الطلبات | غير موجود | Firebase App Check يمنع إساءة استخدام قاعدة البيانات من عملاء غير التطبيق |
| `checkAppointments` | لا تُرسل أي تذكير (أسماء حقول وحالة غير مطابقة) | تُصلَح مع بناء مركز الإشعارات — راجع `functions/README.md` |

## اختبار القواعد محلياً

```bash
firebase emulators:start --only firestore
```

للتحقق من أن القواعد تمنع ما يجب منعه، اكتب اختبارات بـ
`@firebase/rules-unit-testing`. أهم حالة تستحق التغطية: **محاولة تجاوز سعة
الخانة** — وهي الحالة التي يعتمد عليها ضمان عدم الحجز المزدوج.
