# إصدار DrD

إجراء النشر كاملاً، بالترتيب الذي يجب اتّباعه. كل ما هنا **إجراءات يدوية
عليك أنت** — لم يُنفَّذ أيٌّ منها في هذا المستودع.

---

## ما يجب أن تعرفه أولاً

ثلاثة أعطال كانت تمنع نسخة الإصدار من العمل، وثلاثتها **غير مرئية أثناء
التطوير**. أُصلحت الثلاثة، لكن أثنين منها يحتاجان شيئاً منك لا يمكن أن يوجد
في المستودع: مفتاح توقيع، ومفاتيح Firebase للويب.

| العطل | الحالة | ما تحتاجه منك |
|---|---|---|
| `INTERNET` غائب عن بيان الإصدار | ✅ أُصلح | لا شيء |
| توقيع بمفتاح التصحيح | ✅ أُصلح | إنشاء مخزن مفاتيح |
| مفاتيح Firebase للويب فارغة | ✅ أُصلح | تسجيل تطبيق ويب |

الإصلاحان الأخيران **يوقفان البناء برسالة واضحة** بدل إنتاج حزمة معطوبة
بصمت. هذا مقصود: البناء الصامت الخاطئ هو ما سبّب المشكلة أصلاً.

---

## ١. أندرويد

### مرة واحدة: مخزن المفاتيح

```bash
keytool -genkey -v -keystore ~/drd-release.jks \
  -keyalg RSA -keysize 2048 -validity 10000 -alias drd

cp android/key.properties.example android/key.properties
$EDITOR android/key.properties   # املأ المسار وكلمتَي المرور
```

> ⚠ احتفظ بالمخزن ونسخة احتياطية منه إلى الأبد. Google Play يربط التطبيق
> بمفتاح أول إصدار؛ بفقده لا يمكن نشر أي تحديث تحت نفس التطبيق.
> (إن فُعِّل Play App Signing فالمفقود هو مفتاح الرفع وحده، ويمكن استبداله.)

`android/key.properties` و`*.jks` و`*.keystore` مستثناة في `.gitignore`،
ويحرس ذلك `test/android_manifest_test.dart`.

### البناء

```bash
flutter build appbundle --release
```

بلا `key.properties` يتوقّف البناء برسالة تشرح الخطوة الناقصة — ولا يُنتج
حزمة غير موقَّعة.

### تحقّق قبل الرفع

```bash
# الإذن موجود في الحزمة النهائية لا في بيان التصحيح وحده
unzip -p build/app/outputs/bundle/release/app-release.aab \
  base/manifest/AndroidManifest.xml | grep -a INTERNET

# التوقيع ليس مفتاح التصحيح
keytool -printcert -jarfile build/app/outputs/bundle/release/app-release.aab
```

ثم **ثبّت النسخة على هاتف حقيقي وسجّل الدخول**. نجاح تسجيل الدخول هو الدليل
الوحيد على أن الاتصال بـFirebase يعمل في نسخة الإصدار.

### مؤجَّل

`namespace` في `android/app/build.gradle.kts` ما زال
`com.example.medical_appointment_app` (قالب Flutter). تغييره يستلزم نقل
`MainActivity.kt` إلى الحزمة الجديدة **معاً** وإلا انهار التطبيق عند الإقلاع.
لا أثر له على المتجر: Google Play يعتمد `applicationId` وهو `heldoc.com`.

> `applicationId` **لا يتغيّر بعد أول نشر**. إن أردت `com.heldoc` بدل
> `heldoc.com`، فالآن آخر فرصة.

## ٢. الويب

### مرة واحدة: تسجيل تطبيق ويب

مشروع `heldoc-68abf` لا يحتوي على تطبيق ويب مسجَّل، ولهذا كان
`FIREBASE_WEB_API_KEY` فارغاً.

Firebase Console ← Project settings ← Your apps ← Add app ← Web، ثم:

```bash
cp web_config.example.json web_config.json
$EDITOR web_config.json   # املأ apiKey و appId
```

> هذه القيم **ليست أسراراً**: تصل إلى كل متصفح بالضرورة، وما يحمي البيانات
> هو `firestore.rules` وحده. الملف مستثنى من المستودع لأن ربط نسخة البناء
> بمشروع Firebase بعينه قرار نشر، لا ثابت مصدري.

### البناء

```bash
tool/build_web.sh
```

**لا تستخدم `flutter build web --release` مباشرة.** هو ينجح بمفاتيح فارغة
وينتج حزمة تعرض شاشة خطأ لكل زائر — وهو بالضبط العطل الذي كان قائماً.
السكربت يتحقّق أولاً ويرفض البناء عند النقص.

## ٣. ترتيب نشر Firebase — الترتيب إلزامي

الدليل ينتقل من `users` إلى `doctor_profiles`، والمجموعة الجديدة يملأها
محفّز **لا يعمل بأثر رجعي**. النشر بترتيب خاطئ يُفرغ دليل الأطباء.

```bash
# ١ — الدوال أولاً: المحفّز يجب أن يكون حيّاً قبل التعبئة
firebase deploy --only functions

# ٢ — التعبئة: بدونها لا ملفات للأطباء القائمين
node scripts/backfill_doctor_profiles.js            # معاينة
node scripts/backfill_doctor_profiles.js --apply    # تنفيذ

# ٣ — الفهارس: قبل القواعد، فبناء الفهرس يستغرق وقتاً
firebase deploy --only firestore:indexes

# ٤ — القواعد أخيراً
firebase deploy --only firestore:rules

# ٥ — الاستضافة
firebase deploy --only hosting
```

**لماذا القواعد أخيراً:** حتى تلك اللحظة يظل الدليل القديم يقرأ `users` ويعمل.
نشرها أولاً يغلق `users` قبل امتلاء `doctor_profiles` — فيرى المستخدمون دليلاً
فارغاً في النافذة بينهما.

**لماذا الفهارس قبل القواعد:** بناء الفهرس المركّب يستغرق دقائق إلى ساعات حسب
حجم البيانات. استعلام بلا فهرسه يفشل بـ`FAILED_PRECONDITION` — والمحاكي لا
يفرض الفهارس، فهذا الصنف من الأعطال لا يظهر إلا في الإنتاج.

## ٤. الهجرات — بإذن صريح، سكربتاً سكربتاً

أربعة سكربتات لم يُشغَّل أيٌّ منها على أي بيئة. كلها معاينة افتراضياً.

| السكربت | يعالج | إن لم يُشغَّل |
|---|---|---|
| `backfill_doctor_profiles.js` | أطباء بلا ملف عام | **دليل الأطباء فارغ** |
| `backfill_phone_index.js` | حسابات بلا مدخل فهرس | أصحابها محبوسون خارج التطبيق |
| `strip_slot_patient_ids.js` | `patientIds` في خانات قديمة | قائمة حضور كل عيادة مقروءة |
| `migrate_appointment_notes_to_encounters.js` | ملاحظات على المواعيد | سجلات قديمة لا تظهر للمرضى |

وسكربت خامس **للقراءة فقط** ولا يكتب شيئاً بلا معرّفات صريحة:

```bash
node scripts/audit_doctor_accounts.js --json legacy-doctors.json
```

يصنّف كل حساب إلى: طبيب معتمَد · طبيب قديم · مريض · حالة غير متسقة.
«طبيب قديم» = `role == 'doctor'` بلا طلب معتمَد — أي حساب ضغط زر «طبيب» في
شاشة التسجيل القديمة، وما زال يظهر في الدليل ويكتب سجلات سريرية.

**لا يخفض السكربت أي حساب تلقائياً**، لأن بعضهم أطباء حقيقيون زُوِّدوا يدوياً
قبل وجود نظام الطلبات، وخفضهم يقطع عيادة عاملة عن مرضاها. القرار لك، حساباً
حساباً:

```bash
node scripts/audit_doctor_accounts.js --demote uid1,uid2            # معاينة
node scripts/audit_doctor_accounts.js --demote uid1,uid2 --apply    # تنفيذ
```

> خُذ نسخة احتياطية من Firestore قبل أي سكربت بـ`--apply`.

      تحقّق. راجع «مخاطر قائمة» في التقرير النهائي.
- [ ] **نسخ احتياطي مجدول** لـFirestore.
